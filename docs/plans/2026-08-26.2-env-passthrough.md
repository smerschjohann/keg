# keg — Kernel-isolated Execution with Gateways — Implementierungsplan: Host-Env-Steuerung + Repo-Config-Trust

> Operative Ausarbeitung für das Feature „Environment-Steuerung" **plus**
> Repo-Config-Trust:
> 1. **Deny-by-default** für die Host-Env; Passthrough (`env.inherit`,
>    `env.inherit_all`) deklarativ in Repo- **und** User-Config, gemerged,
>    optional pro Lauf per CLI (`-e VAR`/`-e VAR=value`/`--inherit-all`).
> 2. **Trust-Gate auf die ganze `.keg.yaml`:** Jede Änderung (oder neues
>    Repo mit vorhandener Config) erfordert erneutes Trusten. Interaktiv
>    (TTY) wird nachgefragt; non-TTY steigt hart aus, schreibt aber die
>    Checksum. Ein dedizierter Befehl setzt die Checksum explizit.
>
> Sicherheitsinvarianten: `THREAT_MODEL.md` §8 (jede ist regressionsgetestet).
> Arbeitsregeln für Coding-Agents: `AGENTS.md`.
>
> **Status-Tracker:** siehe WP-Köpfe. Stand: **Vollständig umgesetzt (Alle WPs abgeschlossen)**.

## 0. Ausgangslage & Problem

### 0.1 Heutiges Verhalten (Ist)

Der Env-Fluss in die Sandbox ist dreistufig:

1. `orchestrator.BuildArgs` setzt bwrap `--unsetenv` für `HostDeniedEnvVars`
   (`orchestrator.go:61`) plus `Plan.EnvUnset`, dann `--setenv` für
   `Plan.EnvSet` und die Kern-Variablen (HOME, TMPDIR, SHELL, PATH).
2. Der Guest-Prozess erbt dadurch die **komplette Host-Env** minus
   Denied-/Unset-Liste plus Explizits; `prepareGuestProcess` unsets die
   Denied-Liste erneut und wendet den Proxy-Marker an.
3. `runGuestCommandMaybePTY` startet den Workload **ohne `cmd.Env`** — das
   Kind erbt die volle Guest-Env.

**Konsequenz:** Praktisch alle Host-Variablen erreichen den Workload. Das
widerspricht `THREAT_MODEL §8.2` („Keine Erbe-Umgebung; nur explizit
gesetzte Werte"). Ein Repo darf darüber hinaus heute jede Repo-Config
(`.keg.yaml`) ungeprüft verwenden — es gibt keinen Trust-/Änderungs-
schutz, obwohl die Config Mounts, Egress und ab jetzt auch Host-Env-
Passthrough freischaltet.

### 0.2 Ziel (Soll)

* **Deny-by-default:** Ohne Freigabe erreicht den Workload nur die
  keg-definierte Umgebung (Kern + `env.set` + keg-Marker).
* **Passthrough deklarativ** in `.keg.yaml` (Repo) **und** User-Config,
  gemerged; CLI-Override pro Lauf.
* **Trust-Gate auf die ganze, nicht-leere `.keg.yaml`:**
  * Neues Repo mit Config-Datei oder jede inhaltliche Änderung ⇒ erneutes
    Trusten (immer — nicht nur bei Env-Feldern).
  * **TTY:** Nutzer sieht die Config-Änderung und die Checksum, wird
    `ja/nein` gefragt.
  * **Non-TTY:** harter Ausstieg mit Config-Fehler; die Checksum wird dabei
    **geschrieben** (als `current`, siehe 1.3), aber **nicht** freigegeben.
  * **Dedizierter Befehl** `keg trust`, um die Checksum explizit zu
    setzen (für Automatisierung/Non-TTY-Freigabe).
  * Leere/fehlende `.keg.yaml` ⇒ kein Trust nötig (kein Gate).
* **Security-Härte bleibt:** `HostDeniedEnvVars` werden nie per Passthrough
  von der Host-Env übernommen — auch nicht aus der Repo-Config
  (`env.inherit` eines Denied-Namens ⇒ harter Fehler). Explizites Setzen
  (`set`/`-e VAR=value`) eines solchen Namens bleibt möglich.

## 1. Entwurfsentscheidungen

### 1.1 Repo-Config darf Passthrough deklarieren — über den Trust-Gate

`EnvSpec` wird um `Inherit []string` und `InheritAll bool` erweitert und ist
sowohl in der Repo-`.keg.yaml` als auch in der User-Config erlaubt. Der
**Repo-Config-Trust** (ganze Datei) ist die Autorisierungsebene darüber:
Eine `.keg.yaml` wird nur verwendet, wenn ihre aktuelle Checksum der
freigegebenen entspricht. Da das Gate **die ganze Datei** abdeckt, sind damit
alle Freigaben (Mounts, Egress, Env-Passthrough) abgesichert — nicht nur Env.

* **Merge-Reihenfolge (hoch → tief):** CLI > `repos[<match>].env`
  (User-Config) > Repo-`env` (`.keg.yaml`) > User-global `env` >
  Defaults. Die Repo-Config steht über der globalen User-Basis (sie ist durch
  den Trust-Gate autorisiert und regelt sich selbst), unter der spezifischen
  User-Override `repos[]` und CLI.
  `EnvSpec`-Merge: `set` = Map-Merge, `unset` = Union, `inherit` = Union,
  `inheritAll` = true gewinnt (ein `true` irgendwo in der Kette schaltet
  Passthrough ein; siehe Nuance unten).
  *Nuance `inherit_all`: da es den Host-Env-Zugriff „aufmacht", kann ein
  Repo-`inherit_all: true` eine globale `inherit_all: false` überschreiben.
  Dank Trust-Gate vertretbar; ein User kann pro Repo via `repos[<path>]`
  oder CLI gezielt gegensteuern (siehe §14).*
  *Strukturell: Im `BuildPlan` wird die Env-Merge-Kette auf
  `Defaults → User-global → Repo → repos[] → CLI` umgestellt (bisher
  `Repo → effective(User)`) — siehe WP-E4.*

### 1.2 Trust-Persistenz: dedizierte Datei, nicht die User-Config

Der Trust wird **nicht** in die handgepflegte `config.yaml` geschrieben,
sondern in eine eigene, keg-generierte Datei:

```
$XDG_CONFIG_HOME/keg/trust.yaml     # Default; Pfad für Tests überschreibbar
```

Format (YAML, streng; unbekannte Felder ⇒ Lesefehler — Korruption fällt auf):

```yaml
repos:
  /abs/pfad/zum/repo:
    current_sha: "3f9a…"        # SHA-256 der aktuellsten gelesenen Datei
    approved_sha: ""            # SHA-256 der freigegebenen Datei (leer = nie)
    approved_content: |         # Content der freigegebenen Datei (für Diff-Ansicht)
      version: "1"
      env:
        inherit:
          - LANG
    updated: "2026-08-26T19:30:00Z"
```

* **Schlüssel:** realpath des Repo-Roots (eine Quelle der Wahrheit, wie beim
  Repo-Matching).
* **`current_sha`:** SHA-256 über die **rohen Bytes** der ganzen
  (nicht-leeren) `.keg.yaml` — wird bei **jedem** Lauf geschrieben,
  auch wenn der Lauf danach abbricht („Checksum schreiben" im non-TTY-Fall).
* **`approved_sha`:** nur per TTY-Bestätigung **oder** `keg trust`
  gesetzt. `trusted := approved_sha != "" && approved_sha == current_sha`.
* **`approved_content`:** Inhalt der zuletzt freigegebenen Datei — Grundlage
  für die Diff-Ansicht im TTY-Prompt („Config-Änderung ersichtlich").
* **Leere/fehlende Datei:** kein Eintrag (Abwesenheit); nichts zu trusten.

### 1.3 Trust-Gate: Semantik im Detail

Bei jedem Plan-Bau (`run`/Library/Daemon), sobald eine nicht-leere
`.keg.yaml` existiert:

1. `current_sha` der Datei berechnen und **immer** in den Trust-Eintrag
   schreiben (`current_sha`, `updated`) — auch wenn der Lauf danach abbricht.
2. `trusted` prüfen: `approved_sha == current_sha`.
3. Nicht trusted (neues Repo: `approved_sha` leer; geändert:
   `approved_sha != current_sha`) ⇒ **Gate**:
   * **TTY (stdin ist Terminal — `isTerminal`):** Änderung anzeigen
     (Diff: alt `approved_content` → neu; bei neuem Repo „neue Config")
     und darunter die Checksum; Prompt `Trust diese Datei? (ja/nein)`.
     * `ja` ⇒ `approved_sha = current_sha`, `approved_content = Inhalt`,
       weiter ohne Abbruch.
     * `nein` ⇒ Abbruch mit Config-Fehler; `approved_*` bleibt unverändert,
       `current_sha` bleibt geschrieben.
   * **Non-TTY:** Abbruch (hart) mit Config-Fehler, Exit-Code 1, Meldung
     verweist auf `keg trust` bzw. interaktiven Lauf. `current_sha` ist
     bereits geschrieben; `approved_sha` wird **nicht** gesetzt ⇒ weitere
     non-TTY-Läufe bleiben rot, bis explizit freigegeben.
4. `HostDeniedEnvVars`-Passthrough ⇒ harter Config-Fehler (1.7),
   unabhängig vom Trust.

Damit gilt exakt, was gewünscht ist: **immer bei Änderung neu trusten**;
non-TTY „hart aussteigen, aber Checksum schreiben"; interaktiv nachfragen;
Befehl zum expliziten Setzen.

### 1.4 CLI

* `keg run`:
  * `-e NAME=value` → `Plan.EnvSet[NAME]` (explizit setzen),
  * `-e NAME` → `Plan.EnvInherit` (Host-Wert durchreichen),
  * `--inherit-all` → `Plan.EnvInheritAll = true`.
  * Hard-Fehler: Passthrough eines Denied-Namens ⇒ Meldung nennt den Namen,
    verweist auf `-e NAME=value`.
* `keg trust` (dedizierter Befehl zum Setzen der Checksum):
  * `keg trust` (Default: CWD) bzw. `keg trust --repo <path>`:
    berechnet `current_sha` der `.keg.yaml`, setzt `approved_sha` =
    `current_sha` und `approved_content`, gibt die Checksum aus, Exit 0.
  * `keg trust --revoke --repo <path>`: leert `approved_sha` (Trust
    entziehen).
  * `keg trust --status [--repo <path>]`: zeigt `TRUSTED|CHANGED|NONE`
    + Checksum; Exit 0 auch bei `CHANGED`.

### 1.5 `unset`-Semantik unter Deny-by-default

Da Host-Env nicht mehr erbt, ist `env.unset` überflüssig für Host-Leaks,
bleibt aber wirksam und gewinnt Konflikte: Name in `inherit` **und** `unset`
⇒ nicht durchreichen. `set` gewinnt immer über geerbte Werte. „unset-vor-set"
im Arg-Builder bleibt unangetastet.

### 1.6 Was NICHT geändert wird

* Kern-Env (HOME, TMPDIR, SHELL, PATH), `env.set`, `bwrap_args`,
  Template-Env, Port-Env (`KEG_PORT_*`), Secrets-Env, Landlock-Marker:
  bleiben wie heute in `Plan.EnvSet`/`BuildArgs`.
* bwrap `--unsetenv HostDeniedEnvVars` + Guest-Unset bleiben (Defense-in-Depth).
* **Breaking Change (bewusst):** Bisherige „Host-Env erben" entfällt; und
  jede untrusted/geänderte Repo-Config blockiert den Lauf, bis sie getrusted
  ist. Beides ist dokumentierter Bruch (CHANGELOG/README/CONCEPT).

### 1.7 Deny-Härte aus jeder Quelle (+ THREAT_MODEL §8.2)

Die eigentliche Sicherheits-Garantie: **`HostDeniedEnvVars` werden nie per
Passthrough von der Host-Env übernommen** — egal ob `inherit`, `inherit_all`
oder `-e` und egal ob Repo- oder User-Config.

* `env.inherit: [HTTP_PROXY]` / `-e HTTP_PROXY` (Name ⇒ Host-Wert) ist
  **harter Config-Fehler**.
* `env.set: {HTTP_PROXY: "…"}` / `-e HTTP_PROXY=…` bleibt erlaubt
  (host-autorisiert, kein Host-Leak).
* Defense-in-Depth im Guest: Denied-Namen werden nie aus der Guest-Env
  kopiert (bei `inherit` und `all`).
* THREAT_MODEL §8.2 präzisieren (siehe §10).

## 13. Reihenfolge & Schnitte

```
E1 (Config/Merge) → E2 (Trust-Store) → E3 (Gate+Prompt) → E4 (Plan/Marker)
→ E5 (Guest) → E6 (CLI/trust) → E7 (Precedence) → E8 (Integration)
```

* E1/E2/E3 definieren die API und das Gate (Trust zuerst).
* Nach E5 ist Default-Deny im Kern wirksam; E6 macht Gate + CLI nutzbar,

  Doku/THREAT_MODEL im selben Meilenstein (AGENTS §8.4/§8.5).

## 14. Risiken & offene Punkte

* **Non-TTY „Checksum schreiben, aber hart aussteigen":** Umsetzung über
  `current_sha` vs. `approved_sha` — der Lauf bleibt rot, `current_sha` ist
  aber erfasst. Freigabe ausschließlich via TTY-Prompt oder `keg trust`.
  Das ist der Punkt, bei dem ich angenommen habe, dass „Checksum schreiben"
  **nicht** einer Freigabe gleicht — bitte bestätigen (Alternative: Schreiben
  = Auto-Freigabe, dann wäre der Befehl nur Doku).
* **`approved_content` in der Trust-Datei:** nötig für die Diff-Ansicht im
  Prompt („Config-Änderung ersichtlich"). Lokale, user-eigene Datei —
  vertretbar.
* **Trust-Datei-Korruption:** strenges Parsen (unbekannte Felder ⇒ Fehler);
  keine automatische Reparatur (Audit-Integrität); klarer Fehler mit Pfad.
* **Whole-file-Hash:** jede Änderung (auch nicht-Env) erzwingt erneutes
  Trusten — gewollt („immer bei Änderung").
* **Merge-Ordnung Repo > User-global:** Strukturelle Umstellung im
  `BuildPlan` (User-global → Repo → `repos[]` → CLI statt `Repo →
  effective`). Regression: bestehende `env.set`-Konflikte können sich
  umdrehen — durch `TestMergeEnv_*` und `TestBuildPlan_EnvMergeOrder`
  gepinnt.
* **`inherit_all` = true-gewinnt entlang der Kette:** Ein Repo-`true`
  schlägt eine globale `false`. Da das Gate den Host-Env-Zugriff öffnet,
  gezielt gegensteuerbar via `repos[<path>]`/CLI `--inherit-all`; als
  Kompromiss könnte `inherit_all` alternativ „User-global ≥ Repo"
  behandeln — entschieden: true-gewinnt (einfach, trust-gated).
* **Proxy-Variablen sind Denied:** nur über `set`/`-e VAR=value`, nie über
  `inherit` — doppelt abgesichert
  (`TestInvariant_EnvPassthroughDeniedNameRejected` +
  `TestInvariant_GuestStripsHostEnv`).
* **`all`-Modus & interne Marker:** `KEG_*`-Blocklist pflegen;
  benutzer-sichtbare Marker (`KEG_PORT_*`, `CODE_KEG`) durchlassen.
