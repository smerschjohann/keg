## 0. Ausgangslage & Motivation

### 0.1 Ist-Zustand

Mit dem Repository-Trust-Gate prüft `keg` jede nicht-leere `.keg.yaml` kryptografisch via SHA-256 gegen den lokalen Trust-Store (`$XDG_CONFIG_HOME/keg/trust.yaml`). Unbekannte oder geänderte Konfigurationen erfordern eine Freigabe (TTY-Prompt oder `keg trust`).

In Repositories hängen Sicherheitsentscheidungen und Host-Ausführungen jedoch oft nicht nur von `.keg.yaml` ab:
1. **Delegierte Host-Tasks:** Tasks mit `exact` oder `prefixes` in `delegated_tasks` rufen auf dem Host `just <task>` auf, welches das `justfile` ausführt.
2. **Build- und Hilfsskripte:** Repositories können eigene Host-Hooks, Makefiles, Scripts oder Konfigurationsdateien referenzieren, die für Build-, Test- oder Delegationsabläufe relevant sind.

### 0.2 Sicherheitsrisiko

Wenn nur die `.keg.yaml` im Trust-Store erfasst wird, kann ein Angreifer eine referenzierte Datei (z. B. `justfile`, `Makefile`, `scripts/build-host.sh`) manipulieren, ohne `.keg.yaml` anzufassen. Das Trust-Gate würde dies nicht bemerken und potenziell manipulierten Code auf dem Host ausführen.

### 0.3 Ziel (Soll)

* **Generisches Trust-Anchor-Konzept:** Ein Repository kann **beliebige Dateien** als Trust-Anchors deklarieren (`trust_anchors: [...]` in `.keg.yaml`).
* **Automatische Trust-Anchors:** Bei delegierten Just-Tasks (`delegated_tasks.exact` oder `delegated_tasks.prefixes`) wird das `justfile` (bzw. `Justfile`, `.justfile`) automatisch als Trust-Anchor aufgenommen.
* **Kryptografische Überwachung im Trust-Store:** Alle deklarierten und ermittelten Trust-Anchors werden in `trust.yaml` pro Repository mit SHA-256-Checksumme und freigegebenem Inhalt verwaltet.
* **Einheitliches Trust-Gate:**
  * Ist `.keg.yaml` ODER ein beliebiger Trust-Anchor neu oder verändert, blockiert das Gate im Non-TTY-Modus oder fordert im TTY-Modus die Bestätigung aller Änderungen an.
  * `keg trust` genehmigt `.keg.yaml` sowie alle aktiven Trust-Anchors in einem atomaren Schritt.
  * `keg trust --status` gibt den Zustand aller Trust-Anchors transparent aus.
  * `keg trust --revoke` entzieht den Trust für das gesamte Repository inkl. aller Trust-Anchors.

## 1. Entwurfsentscheidungen

### 1.1 Konfiguration in `.keg.yaml`

Neues optionales Feld `trust_anchors` in `Repo` (`internal/config/types.go`):

```yaml
version: "1"

# Beliebige Dateien im Repo, die kryptografisch überwacht werden müssen:
trust_anchors:
  - justfile
  - Makefile
  - scripts/prepare-host.sh

delegated_tasks:
  exact:
    - container-build
```

**Regeln für `trust_anchors`:**
1. Pfade sind relativ zum Repository-Root.
2. Pfad-Traversal über den Repo-Root hinaus (`..`) ist unzulässig (Validierungsfehler).
3. Auto-Detection: Wenn `delegated_tasks.exact` oder `delegated_tasks.prefixes` nicht leer ist und ein `justfile` im Repo-Root existiert, wird `justfile` automatisch zu den Trust-Anchors hinzugefügt, falls nicht bereits explizit gelistet.

### 1.2 Datenmodell im Trust-Store (`trust.yaml`)

Struktur von `internal/trust`:

```yaml
repos:
  /abs/pfad/zum/repo:
    current_sha: "3f9a…"        # SHA-256 von .keg.yaml
    approved_sha: "3f9a…"       # Freigegebene SHA-256 von .keg.yaml
    approved_content: |         # Inhalt von .keg.yaml
      version: "1"
      trust_anchors:
        - scripts/build.sh
    anchors:                    # Generische Map weiterer Trust-Anchors
      scripts/build.sh:
        current_sha: "b81c…"
        approved_sha: "b81c…"
        approved_content: |
          #!/bin/bash
          echo "Building..."
      justfile:
        current_sha: "a71b…"
        approved_sha: "a71b…"
        approved_content: |
          container-build:
              podman build .
    updated: "2026-08-27T16:30:00Z"
```

Go-Typen:

```go
type AnchorEntry struct {
    CurrentSHA      string `yaml:"current_sha"`
    ApprovedSHA     string `yaml:"approved_sha"`
    ApprovedContent string `yaml:"approved_content"`
}

type Entry struct {
    CurrentSHA      string                 `yaml:"current_sha"`
    ApprovedSHA     string                 `yaml:"approved_sha"`
    ApprovedContent string                 `yaml:"approved_content"`
    Anchors         map[string]AnchorEntry `yaml:"anchors,omitempty"`
    Updated         time.Time              `yaml:"updated"`
}
```

* Vollständig abwärtskompatibel zu bestehenden `trust.yaml`-Dateien.
* Sortierte Speicherung der Anchor-Keys für deterministisches YAML.

### 1.3 Trust-Status-Berechnung

Ein Repository gilt als `TRUSTED`, wenn:
1. `approved_sha != "" && approved_sha == current_sha` (für `.keg.yaml`), **UND**
2. Für **jeden** aktiven Trust-Anchor gilt:
   `anchor.ApprovedSHA != "" && anchor.ApprovedSHA == anchor.CurrentSHA`.

Sobald ein Anchor fehlt, verändert wurde oder unbestätigt ist, gilt das Repository als `CHANGED` bzw. `NONE`.

### 1.4 Prüfzeitpunkte (Wann wird geprüft?)

Die Integrität der Trust-Anchors wird an zwei essenziellen Stellen geprüft:

1. **Initial beim Sandbox-Start (`BuildPlan` / `keg run`):**
   * Bevor die Sandbox hochgefahren wird, werden `.keg.yaml` und alle deklarierten/automatischen Trust-Anchors (`justfile`, `Makefile` etc.) geprüft.
   * **TTY:** Zeigt Diffs aller geänderten Dateien; interaktive Bestätigung `ja/nein`.
   * **Non-TTY:** Bricht sofort hart ab (Exit 1) mit Hinweis auf `keg trust`.
2. **Laufzeit-Prüfung vor jedem delegierten Host-Aufruf (`internal/runner/server.go` vor `buildCommand`/`runJob`):**
   * Wenn ein Prozess aus der Sandbox via Kanal C (`keg delegate <task>`) eine Host-Ausführung anfordert (insb. Just-Rezepte oder von Anchors abhängige Tasks), verifiziert der Host-Runner unmittelbar vor der Ausführung die Checksumme der relevanten Trust-Anchor-Dateien (z. B. `justfile`) auf dem Host.
   * **Warum?** Verhindert Runtime-Tampering: Ein Prozess innerhalb der Sandbox (oder ein paralleler Prozess) könnte während des Laufs das `justfile` im Arbeitsverzeichnis manipuliert haben.
   * **Verhalten bei Modifikation:** Harter Abbruch / Ablehnung der Ausführung (Fail-Closed, Exit-Code 126 / `EventError` über Kanal C), da im IPC-Kanal keine interaktive TTY-Rückfrage mehr stattfinden darf.
3. **Explizit per CLI (`keg trust` / `keg trust --status`):**
   * Zur manuellen Vorab-Genehmigung oder Statusprüfung auf dem Host.
