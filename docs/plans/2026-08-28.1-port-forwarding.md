# keg — Kernel-isolated Execution with Gateways — Implementierungsplan: Port-Publishing & Port-Forwarding (Host ⇄ Sandbox)

> Operative Ausarbeitung für flexible Port-Weiterleitungen nach Docker- und SSH-Vorbild:
> **1. Erweitertes Port-Publishing (Host → Sandbox) mit Unterstützung beliebiger Bind-Adressen (`[host_ip:]host_port:container_port`),**
> **2. Host-Service-Forwarding in die Sandbox (Sandbox → Host/Netzwerk) via SSH-Muster (`-L sandbox_port:target_host:target_port`).**
>

## 0. Ausgangslage & Motivation

### 0.1 Ist-Zustand

In `keg` existiert aktuell der **Kanal E (`portsfw`)** als Rückkanal für Dev-Server (z. B. Playwright-Workflows):
* **Host-seitig:** Exponiert Sandbox-Dienste auf dem Host.
* **CLI:** `-p <host>:<guest>` bzw. `-p <port>` (z. B. `-p 8080`, `-p 3000:80`).
* **YAML (`.keg.yaml`):** `ports: ["3000"]` oder `ports: ["5432:15432"]` (im YAML als `<guest>:<host>`).
* **Dynamische Ports:** `ports: [{name: "dev", dynamic: true}]` mit Export als `KEG_PORT_<NAME>`.

### 0.2 Defizite & Limitationen

1. **Keine Bindung an externe Host-IPs (`any-ip:port`):**
   * Der Host-Listener bindet in `StartPortsForward` hart auf `127.0.0.1`.
   * Der Parser `ParsePublishFlag` (`internal/config/expand.go`) lehnt jede Nicht-Loopback-IP (z. B. `0.0.0.0`, LAN-IPs wie `192.168.1.50`) mit Fehler ab:
     `"keg only binds on loopback (127.0.0.1)"`.
   * Szenarien, in denen eine Sandbox über das lokale Netzwerk oder auf spezifischen Interfaces erreichbar sein soll (Docker-Muster `-p 0.0.0.0:1234:2345`), sind nicht möglich.

2. **Keine Weiterleitung lokaler/externer Host-Ports IN die Sandbox (Guest → Host/Any-IP):**
   * Läuft auf dem Host oder im lokalen Netzwerk ein Dienst (z. B. Host-PostgreSQL auf `127.0.0.1:5432`, ein lokaler Mock-Server oder ein Firmen-Backend auf `10.0.0.5:1234`), kann die Sandbox diesen **nicht** direkt über Loopback ansprechen.
   * Da in der Sandbox `--unshare-net` aktiv ist, hat die Sandbox nur ihr eigenes isoliertes Loopback-Interface.
   * Egress existiert bisher nur für HTTP/HTTPS-Domains (Kanal A) und DNS-korrelierte raw-TCP-Endpoints (Transparent-Modus).
   * Es gibt **keine Möglichkeit**, einen lokalen Host- oder Netzwerk-Port in die Sandbox zu mappen (z. B. SSH `-L 2345:127.0.0.1:1234` oder `-L 2345:10.0.0.5:1234`), sodass ein Tool in der Sandbox auf `127.0.0.1:2345` zugreift und transparent mit dem Ziel verbunden wird.

3. **Inkonsistente Syntax-Konvention:**
   * CLI `-p` nutzt das Docker-Format: `<host_port>:<container_port>`.
   * `.keg.yaml` nutzt historisch `<guest_port>:<host_port>`.
   * Eine Vereinheitlichung und Unterstützung des Standard-Docker- und SSH-Schemas ist erforderlich.

### 0.3 Ziel (Soll)

* **Richtung 1 (Publishing: Host → Sandbox):**
  * Volle Unterstützung von Docker-kompatiblen Port-Spezifikationen:
    `[host_ip:][host_port:]container_port[/tcp]`.
  * Freigabe konfigurierbarer Host-IPs (`0.0.0.0`, `127.0.0.1`, LAN-IPs) mit sicherem Default (`127.0.0.1`).
* **Richtung 2 (Forwarding: Sandbox → Host / Any-IP):**
  * Unterstützung von SSH-kompatiblem Port-Forwarding in die Sandbox:
    `-L [guest_ip:]guest_port:target_host:target_port` (bzw. `--forward-host` / `forward_hosts` in Config).
  * Ein Prozess in der Sandbox kann `127.0.0.1:guest_port` ansprechen; der Host-Daemon verbindet den Stream zum deklarierten Ziel `target_host:target_port`.
* **Sicherheitsgarantien & Invarianten:**
  * Deny-by-default: Nur explizit deklarierte Ports werden weitergeleitet.
  * Audit-Logging für alle aufgebauten Verbindungen.
  * Kein impliziter Bypass der Egress-Policy; Forwarding-Ziele müssen in `.keg.yaml` oder via CLI explizit freigegeben werden.

## 1. Entwurfsentscheidungen & Spezifikation

### 1.1 CLI-Syntax

Die CLI unterstützt zwei komplementäre Flags nach etablierten Vorbildern:

#### A. Port-Publishing (Host → Sandbox, Docker-Muster `-p` / `--publish`)
Exponiert einen Sandbox-Service auf dem Host:
```bash
# Sandbox 2345 auf Host 127.0.0.1:1234 bereitstellen (Default-IP ist 127.0.0.1)
keg run -p 1234:2345

# Sandbox 2345 auf ALLEN Host-Interfaces (0.0.0.0) unter Port 1234 bereitstellen
keg run -p 0.0.0.0:1234:2345

# Sandbox 2345 auf spezifischer Host-IP bereitstellen
keg run -p 192.168.1.50:1234:2345

# Dynamischer Host-Port (auf 127.0.0.1) für Sandbox 2345
keg run -p :2345
```

#### B. Host-Port-Forwarding (Sandbox → Host / Any-IP, SSH-Muster `-L` / `--forward-host`)
Leitet Verbindungen aus der Sandbox an einen Host-/Netzwerk-Dienst weiter:
```bash
# Sandbox-Port 2345 leitet weiter an Host 127.0.0.1:1234
keg run -L 2345:127.0.0.1:1234

# Sandbox-Port 2345 leitet weiter an externe IP/Host im Netzwerk
keg run -L 2345:db.internal:5432
keg run -L 2345:10.0.0.5:1234

# Kurzform: Sandbox-Port = Target-Port auf Host-Loopback (z.B. 5432 -> 127.0.0.1:5432)
keg run -L 5432:127.0.0.1:5432
```

### 1.2 Konfiguration in `.keg.yaml`

Erweiterung der Konfigurationsstruktur in `internal/config/types.go`:

```yaml
version: "1"

# 1. Publishing: Sandbox-Services auf dem Host exponieren (Host -> Sandbox)
ports:
  # Standard: Sandbox 2345 -> Host 127.0.0.1:1234
  - host_ip: "127.0.0.1"    # optional, Default: 127.0.0.1
    host_port: 1234
    guest_port: 2345
  # Beliebige Host-IP (0.0.0.0 oder Interface-IP)
  - host_ip: "0.0.0.0"
    host_port: 8080
    guest_port: 8080
  # String-Kurzformen nach Docker-Muster:
  - "1234:2345"             # 127.0.0.1:1234 -> Sandbox:2345
  - "0.0.0.0:8080:80"       # 0.0.0.0:8080 -> Sandbox:80
  # Dynamischer Port mit Environment-Export:
  - name: dev-server
    guest_port: 3000
    dynamic: true           # exportiert KEG_PORT_DEV_SERVER auf dem Host

# 2. Forwarding: Host-/Netzwerk-Dienste in die Sandbox leiten (Sandbox -> Host/Ziel)
forward_hosts:
  # Sandbox 127.0.0.1:2345 leitet weiter an Host 127.0.0.1:1234
  - guest_port: 2345
    target_host: "127.0.0.1"
    target_port: 1234
  # Sandbox 127.0.0.1:5432 leitet an Remote-Datenbank weiter
  - guest_port: 5432
    target_host: "db.corp.internal"
    target_port: 5432
  # String-Kurzform nach SSH-Muster:
  - "2345:127.0.0.1:1234"
  - "5432:db.corp.internal:5432"
```

### 1.3 Architektur & Datenfluss

```
========================================================================================
1. PORT PUBLISHING (Host -> Sandbox über Kanal E)
========================================================================================
Host Client (z.B. Browser)
       │
       ▼ connect [host_ip]:[host_port] (z.B. 0.0.0.0:1234 oder 127.0.0.1:1234)
Host Listener (keg)
       │
       ▼ muxado Stream über FDPorts (Kanal E)
Guest Forwarder (keg entrypoint in Sandbox)
       │
       ▼ dial 127.0.0.1:[guest_port] (z.B. 127.0.0.1:2345)
Dev-Server in Sandbox

========================================================================================
2. HOST PORT FORWARDING (Sandbox -> Host/Ziel über Kanal F)
========================================================================================
App / Tool in Sandbox (z.B. psql, curl)
       │
       ▼ connect 127.0.0.1:[guest_port] (z.B. 127.0.0.1:2345)
Guest Inbound-Listener (keg entrypoint in Sandbox)
       │
       ▼ muxado Stream über FDHostForward (Kanal F)
Host Forwarder (keg auf Host)
       │
       ▼ dial [target_host]:[target_port] (z.B. 127.0.0.1:1234 oder 10.0.0.5:1234)
Host-Service oder Netzwerk-Ziel
========================================================================================
```

#### Deskriptor-Belegung (Erweiterung in `internal/orchestrator`):
* `fd 3`: `FDProxy` (Kanal A: HTTP/HTTPS Whitelist Egress)
* `fd 4`: `FDDNS` (Kanal B: DNS Bridge)
* `fd 5`: `FDRunner` (Kanal C: Delegated Host Tasks)
* `fd 6`: `FDAgent` (Kanal D: Guest Control)
* `fd 7`: `FDPorts` (Kanal E: Port Publishing Host → Sandbox)
* `fd 8`: `FDHostForward` (Kanal F: Port Forwarding Sandbox → Host/Ziel)

### 1.4 Sicherheitsmodell & Bedrohungsanalyse (`THREAT_MODEL.md`)

| Bedrohung / Risiko | Bewertung | Gegenmaßnahme |
|---|---|---|
| **Exposition auf `0.0.0.0`:** Unerwünschte Erreichbarkeit aus dem lokalen Netzwerk | Mittel | Standard bleibt `127.0.0.1`. Bindung an `0.0.0.0` erfordert explizite Angabe der IP im Flag/Config. Audit-Log dokumentiert Bind-Adresse. |
| **Sandbox nutzt Forwarding für unkontrollierten Host-Egress:** Ausbruch aus Netzwerk-Isolation | Hoch | **Strict Whitelist:** Nur deklarierte `forward_hosts` werden vom Host-Forwarder akzeptiert. Der Guest-Listener bindet ausschließlich `127.0.0.1` in der Sandbox. Host-Forwarder verweigert Ziele außerhalb der Whitelist fail-closed. |
| **Angriff auf Host-Loopback-Services (z.B. Docker Socket, Cloud Metadata):** Sandbox erreicht interne Host-APIs | Hoch | Audit-Logging für alle Host-Dials; Deaktivierbar per User-Config `security.allow_host_forward: false`. Validierung von verbotenen Host-Zielen konfigurierbar. |
| **Port-Kollisionen auf dem Host:** Belegte Ports blockieren Start | Niedrig | Eindeutige Fehlermeldung mit Fehlercode `E_PORT_CONFLICT`; Option `dynamic: true` für automatische freie Port-Wahl. |

* **Tasks:**
  1. `internal/config/types.go`:

     * Neue Struktur `ForwardHostSpec` (`GuestPort int`, `TargetHost string`, `TargetPort int`).
     * `Repo`-Struct um `ForwardHosts []ForwardHostSpec` erweitern.
  2. `internal/config/expand.go`:
     * Überarbeitung von `ParsePublishFlag`: Erlaubt `0.0.0.0` und beliebige IPv4/IPv6-Adressen für Host-Bindung; Default ist `127.0.0.1`.

       * Parst `guest_port:target_host:target_port` (z. B. `2345:127.0.0.1:1234` oder `2345:db.internal:5432`).
       * Validiert Portbereiche (1..65535) und Hostnamen.

* **DoD:**

### WP 2: Host-IP Binding im Port-Publishing (`internal/portsfw`)

* **Tasks:**

### WP 3: Inbound Host-Port Forwarding Kanal F (`internal/portsfw`)

**Ziel:** Implementierung des Reverse-Forwarders von der Sandbox zum Host.

* **Tasks:**
  1. `internal/portsfw/reverse.go`:
     * `ServeHostForwarder(ctx, sess muxado.Session, allowed []ForwardHostSpec, dial DialFunc)`:
       * Host-seitiger Server für Kanal F.
       * Liest 2-Byte Guest-Port-Header aus eingehendem Muxado-Stream.
       * Prüft gegen Allowlist der erlaubten `forward_hosts`.
       * Öffnet TCP-Verbindung zu `target_host:target_port` und tunnelt bidirektional via `tunnel(stream, targetConn)`.
     * `StartGuestForwarder(ctx, sess muxado.Session, specs []ForwardHostSpec)`:
       * Gast-seitiger Forwarder (läuft im Sandbox-Entrypoint).
       * Bindet lokale TCP-Listener auf `127.0.0.1:<guest_port>` in der Sandbox.
       * Bei eingehender Verbindung: Öffnet Muxado-Stream auf Kanal F, schreibt Header und tunnelt Daten.
  2. Protokoll-Framing:
     * Wiederverwendung des 2-Byte-Big-Endian-Port-Headers (`EncodeTarget` / `DecodeTarget`).
* **DoD:**
  * Unit-Tests in `internal/portsfw/reverse_test.go` mit In-Memory-Pipes und Mock-Netzwerk.
  * Deny-by-default-Test: Nicht deklarierte Ports werden fail-closed abgewiesen.
  * `go test -race ./internal/portsfw/...` grün.
