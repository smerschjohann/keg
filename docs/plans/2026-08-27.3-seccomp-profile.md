## 0. Ausgangslage & Motivation

### 0.1 Ist-Zustand

keg isoliert Dateisystem (Positivlisten-Mounts + Landlock), Netzwerk
(`--unshare-net`, Whitelist-Proxy/DNS), Prozessraum (`--unshare-all`) und
Namespace-Eskalation (`--disable-userns`, doppelt abgesichert über
Wirts-Sysctl). Der Workload läuft ohne Capabilities (`CapBnd=0`), mit
`NoNewPrivs=1` und unter einem whitelisted Delegations-Kanal.

Verifiziert durch unabhängige Agenten-Recon (2026-08-27) in einer laufenden
`keg run`-Sandbox: kein klassischer Escape-Pfad (UserNS blockiert, keine
SUID-Wirkung, keine IPC-Sockets, kein Egress außerhalb der Kanäle).

### 0.2 Sicherheitslücke

**Kein Seccomp-Filter** (`Seccomp: 0` in `/proc/self/status`). Landlock
beschränkt den Dateisystem-Zugriff auf Syscall-Ebene, filtert aber die
übrige Kernel-Angriffsfläche nicht. Adressierbar bleiben u. a.:

| Syscall | Risiko ohne Filter |
|---|---|
| `bpf` | eBPF-Loads/Map-Zugriff; Kernel-Parser & JIT-Angriffsfläche |
| `perf_event_open` | Kernel-Profiling/-Tracing, Side-Channels |
| `io_uring_setup` etc. | Großer, junger Code-Pfad mit LPE-Historie |
| `ptrace`, `process_vm_readv/writev` | Prozess-Inspektion jenseits PID-NS-Grenzen |
| `keyctl`, `add_key`, `request_key` | Kernel-Keyring (persistent, nutzerübergreifend) |
| `userfaultfd` | Heap-Spray-Primitive für Race-Exploits |
| `kexec_load`, `init_module`, `finit_module`, `delete_module` | Kernel-Modul-/Image-Wechsel |
| `mount`, `pivot_root`, `swapon`, `reboot` | Mount-/HA-Wirkung (bereits durch fehlende Caps wirkungslos, aber Codepfad erreicht Parser) |
| `unshare`/`clone3` mit `CLONE_NEWUSER` | Bereits doppelt geblockt (`--disable-userns`, Wirt-Sysctl) |

Annahme A1 (Kernel gilt als vertrauenswürdig) bleibt; der Filter reduziert
die Fläche, auf der diese Annahme belastet wird. Das ist die vom Recon
identifizierte verbliebene realistische Angriffsklasse (Kernel-Syscall-LPE).

### 0.3 Ziel (Soll)

* Der Workload läuft unter einem **Default-Allow-/Blocklisten**-Seccomp-BPF-Programm
  mit `SECCOMP_RET_ERRNO | EPERM` für die kritischen Syscalls.
* bwrap erhält das Programm via **`--add-seccomp-fd FD`** (ab 0.11
  verfügbar; Verfügbarkeit durch WP-M8b-`CheckBwrapVersion` erzwungen).
* Komplett In-Process: kein libseccomp-Binding — cBPF-Bytecode manuell
  via `golang.org/x/sys/unix`-Konstanten gebaut (Budget §1 bleibt
  geschlossen, keine neue Dependency).
* Deaktivierung **ausschließlich** per User-Config `security.seccomp: off`
  (Invariante 4; Repo-Config kann die Isolation nie lockern).
* Kein Bruch legitimer Dev-Workloads: Toolchain-Tests in den
  Integrationstests sichern Go/Shell/Git-Funktionalität unter dem Filter.

## 1. Entwurfsentscheidungen

### 1.1 Filterform: Default-Allow + Blockliste (bewusster Trade-off)

Default-Deny mit Allowlist wäre ideal (Docker-Default-Profil als Referenz),
bricht aber Dev-Toolchains unvorhersehbar (jedes neue Runtime-Feature
scheitert stumm; schwer wartbar ohne libseccomp). Gewählt wird:

* **Default: `SECCOMP_RET_ALLOW`**
* **Blockliste** (~15 Syscalls, siehe §0.2) → `SECCOMP_RET_ERRNO | EPERM`
* EPERM statt KILL: Programme, die Feature-Detection über Fehler machen,
  bleiben funktional; Testbarkeit einfacher (EPERM assertbar).
* Architektur-Check: Filter prüft `audit arch` — nicht-native
  Arch-Syscalls (z. B. x86-32 auf x86-64) fallen in die Blockliste.

Begründung im Plan festhalten; bei späterer Verschärfung Richtung
Docker-Default bleibt die Schnittstelle (`Profil`-Struct) gleich.

### 1.2 Übergabeweg: `--add-seccomp-fd`

bwrap ≥ 0.11 nimmt ein cBPF-Programm als Datei-Deskriptor entgegen (`--add-seccomp-fd`,
wiederholbar; `--seccomp` setzt Basis). keg übergibt das Programm
als Pipe/memfd-FD aus der Parent-Seite, analog zum `FDProxy/FDDNS`-Pattern:

```
Host: keg kompiliert Profil → memfd_create → write →
      bwrap argv += "--add-seccomp-fd 7"
      cmd.ExtraFiles = append(cmd.ExtraFiles, memfd) // → fd 7 im bwrap
```

Vorteile gegenüber Datei-Pfaden: nichts auf Disk, keine temporären
Artefakte, FD schließt mit Sandbox-Exit (Invariante 8). bwrap installiert
den Filter *vor* dem exec des Guests mit `no_new_privs` (Landlock setzt das
bereits; kumulative Filter wirken multiplikativ).

### 1.3 Paket & Schnittstelle

Neues Paket `internal/seccomp` — reine Kerne, kein I/O außer im
Compiler-Wrapper:

```go
// internal/seccomp/profile.go
type Profile struct {
    DefaultAction uint32            // SECCOMP_RET_ALLOW
    BlockedSyscalls []SyscallRule   // name → errno (default EPERM)
}

// Compiler erzeugt die cBPF-Bytefolge (little-endian sock_filter-Slices,
// wie seccomp_data-Semantik: nr, arch, instruction_pointer, args[6]).
func Compile(p Profile, nativeArch uint32) ([]byte, error)
```

`internal/orchestrator` nutzt:

* `seccomp.Compile(seccomp.DefaultProfile(), unix.AUDIT_ARCH_X86_64)`
* memfd-Setup in `launch.go`, FD-Nummer ↔ `--add-seccomp-fd N`
* Config-Flag `security.seccomp: off` deaktiviert sowohl Compile als auch
  das Flag (kein stiller Fallback; wenn an, muss Compile gelingen).

### 1.4 Config-Schema

User-Config (vertrauenswürdig, `~/.config/keg/config.yaml`):

```yaml
security:
  seccomp: auto   # auto (default: an wenn bwrap >= 0.11)
                  # off  (nur User-Config; Repo kann nicht lockern)
```

**Kein** Repo-Config-Feld. Strict-Decoding lehnt `seccomp` in `.keg.yaml`
als unbekanntes Feld ab — sichtbar, keine stille Ignorierung (Invariante 4).

### 1.5 Invariante 9 (THREAT_MODEL §8, im selben PR nachziehen)

> „Der Workload läuft unter einem Syscall-Filter (Seccomp-BPF), der die
> Kernel-Angriffsfläche auf das für Dev-Workloads notwendige Maß reduziert;
> nur die vertrauenswürdige User-Config kann den Filter deaktivieren. Die
> Deaktivierung ist nie still: Audit-Log und Start-Output benennen sie."

THREAT_MODEL §5.1 erhält eine Seccomp-Zeile; §7 Residualrisiko
„Kernel-Codepfade außerhalb der Blockliste (Parser, Netz, VFS intern)"
bleibt unter A1.
